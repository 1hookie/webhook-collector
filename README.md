# WebHook Collector

Сервис для приёма и просмотра веб-хуков, по аналогии с [webhook.site](https://webhook.site)

Hookcatcher выдаёт уникальный URL, принимает на него HTTP-запросы любым методом и сохраняет их целиком: метод, путь, заголовки, тело, IP и время. Через API можно посмотреть, что пришло. Удобно для отладки интеграций с GitHub, Stripe, Telegram и любыми другими сервисами, которые шлют веб-хуки.

## Возможности

- Создание каналов с уникальным UUID и готовым URL для приёма.
- Приём запросов любым HTTP-методом: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` и другими.
- Сохранение тела без разбора, поэтому формат не важен: JSON, form-data, XML, текст.
- Сохранение всех заголовков, query-параметров и IP отправителя, с учётом `X-Forwarded-For` и `X-Real-IP`.
- Просмотр истории запросов канала в JSON.
- Настройка через файл и переменные окружения, готовность к запуску в контейнере.
- Потокобезопасное хранилище с ограничением числа запросов на канал.

## Быстрый старт

### Требования

- Go 1.22 или новее
- `curl` для проверки; `jq` по желанию

### Установка и запуск

```bash
git clone <repo-url> hookcatcher
cd hookcatcher

go mod download
go run .
```

По умолчанию сервер слушает порт `8080`:

```
listening on :8080, base_url=http://localhost:8080
⇨ http server started on [::]:8080
```

### Сборка бинарника

```bash
go build -o hookcatcher .
./hookcatcher
```

Файл `config.json` должен лежать в директории запуска, либо путь к нему передаётся через `HC_CONFIG_FILE`.

### Первый веб-хук

```bash
# 1. Создать канал
ID=$(curl -s -X POST http://localhost:8080/api/v1/hooks | jq -r .id)

# 2. Отправить в него запрос
curl -X POST http://localhost:8080/wh/$ID \
  -H "Content-Type: application/json" \
  -d '{"event":"payment.succeeded","amount":100}'

# 3. Посмотреть, что пришло
curl -s http://localhost:8080/api/v1/hooks/$ID/requests | jq
```

## Конфигурация

Настройки загружаются в таком порядке, каждый следующий шаг перекрывает предыдущий:

1. файл `config.json`;
2. переменные окружения `HC_*`;
3. вычисляемые значения по умолчанию;
4. валидация.

Если конфигурация некорректна, сервис не запускается и выводит причину.

### Файл конфигурации

```json
{
    "port": 8080,
    "base_url": "",
    "db": {
        "host": "localhost",
        "port": 5432,
        "DBName": "hookcatcher",
        "user": "hookcatcher",
        "password": "hookcatcher"
    }
}
```

| Параметр | Тип | Описание |
|---|---|---|
| `port` | int | порт HTTP-сервера, `1..65535` |
| `base_url` | string | публичный адрес сервиса для сборки URL каналов; если пусто — `http://localhost:<port>` |
| `db.host` | string | хост PostgreSQL |
| `db.port` | int | порт PostgreSQL, `1..65535` |
| `db.DBName` | string | имя базы данных |
| `db.user` | string | пользователь |
| `db.password` | string | пароль |

> Секция `db` пока не используется сервисом, но проверяется при запуске.

### Переменные окружения

| Переменная | Параметр |
|---|---|
| `HC_CONFIG_FILE` | путь к файлу конфигурации (по умолчанию `config.json`) |
| `HC_PORT` | `port` |
| `HC_BASE_URL` | `base_url` |
| `HC_DB_HOST` | `db.host` |
| `HC_DB_PORT` | `db.port` |
| `HC_DB_NAME` | `db.DBName` |
| `HC_DB_USER` | `db.user` |
| `HC_DB_PASSWORD` | `db.password` |

Пустые и некорректные значения игнорируются, остаётся значение из файла.

### Примеры

```bash
# Другой порт: меняется и порт сервера, и base_url
HC_PORT=8090 go run .

# Сервис за обратным прокси с публичным доменом
HC_BASE_URL=https://hooks.example.com go run .

# Отдельный файл конфигурации
HC_CONFIG_FILE=/etc/hookcatcher/config.json ./hookcatcher
```

### Почему `base_url` задаётся в конфиге

URL каналов собирается из `base_url`, а не из заголовка `Host` входящего запроса. За прокси или балансировщиком сервис видит внутренний адрес, а заголовок `Host` может прислать кто угодно. Адрес из конфигурации задаёт администратор, поэтому он надёжен.

## API

Все ответы в формате JSON.

### Обзор

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/v1/hooks` | создать канал |
| `ANY` | `/wh/{id}` | принять веб-хук |
| `GET` | `/api/v1/hooks/{id}/requests` | получить запросы канала |

---

### `POST /api/v1/hooks`

Создаёт новый канал.

**Запрос**

```bash
curl -X POST http://localhost:8080/api/v1/hooks
```

**Ответ** `201 Created`

```json
{
  "status": true,
  "id": "6f1c2a9e-4b7d-4e2a-9c3f-1a2b3c4d5e6f",
  "url": "http://localhost:8080/wh/6f1c2a9e-4b7d-4e2a-9c3f-1a2b3c4d5e6f"
}
```

| Поле | Описание |
|---|---|
| `status` | признак успеха |
| `id` | идентификатор канала (UUID v4) |
| `url` | адрес для отправки веб-хуков |

---

### `ANY /wh/{id}`

Принимает запрос любым методом с любым телом и сохраняет его в канал.

**Запрос**

```bash
curl -X POST "http://localhost:8080/wh/$ID?source=github" \
  -H "Content-Type: application/json" \
  -d '{"action":"opened"}'
```

**Ответы**

| Код | Тело | Когда |
|---|---|---|
| `200 OK` | `{"status":true}` | запрос сохранён |
| `400 Bad Request` | `{"status":false,"error":"cannot read body"}` | не удалось прочитать тело |
| `404 Not Found` | `{"status":false,"error":"hook not found"}` | канала не существует |

Канал хранит до 100 последних запросов, более старые вытесняются.

---

### `GET /api/v1/hooks/{id}/requests`

Возвращает сохранённые запросы канала в порядке поступления.

**Запрос**

```bash
curl http://localhost:8080/api/v1/hooks/$ID/requests
```

**Ответ** `200 OK`

```json
[
  {
    "method": "POST",
    "path": "/wh/6f1c2a9e-4b7d-4e2a-9c3f-1a2b3c4d5e6f?source=github",
    "headers": {
      "Content-Type": "application/json",
      "Host": "localhost:8080",
      "User-Agent": "curl/8.4.0"
    },
    "body": "{\"action\":\"opened\"}",
    "ip": "127.0.0.1",
    "received_at": "2026-11-04T12:00:00.123456+03:00"
  }
]
```

Если запросов нет, возвращается пустой массив `[]`.

| Поле | Тип | Описание |
|---|---|---|
| `method` | string | HTTP-метод |
| `path` | string | путь вместе с query-строкой |
| `headers` | object | заголовки; повторяющиеся объединены через `", "` |
| `body` | string | тело запроса без изменений |
| `ip` | string | IP отправителя |
| `received_at` | string | время приёма, RFC 3339 |

**Ошибки**

| Код | Тело |
|---|---|
| `404 Not Found` | `{"status":false,"error":"hook not found"}` |

## Архитектура

### Структура проекта

```
.
├── main.go                  точка входа и сборка зависимостей
├── config.json              конфигурация по умолчанию
├── config/
│   ├── config.go            загрузка, переменные окружения, валидация
│   └── config_test.go
├── model/
│   ├── model.go             модели Hook и WebhookRequest
│   ├── url.go               сборка URL канала
│   └── url_test.go
├── storage/
│   └── memory.go            хранилище в памяти
└── controller/
    └── controller.go        HTTP-обработчики
```

### Слои

```
            ┌──────────────┐
  HTTP ───► │  controller  │  разбор запроса, коды ответов, JSON
            └──────┬───────┘
                   │
            ┌──────▼───────┐
            │   storage    │  хранение, потокобезопасность
            └──────┬───────┘
                   │
            ┌──────▼───────┐
            │    model     │  структуры данных, сборка URL
            └──────────────┘

  config ──► main ──► собирает всё вместе
```

| Пакет | Ответственность |
|---|---|
| `config` | откуда брать настройки и корректны ли они |
| `model` | формат данных и их представление в JSON |
| `storage` | хранение каналов и запросов, синхронизация доступа |
| `controller` | HTTP-слой: входящие запросы и ответы |

Зависимости создаются конструкторами в `main.go` и передаются явно:

```go
cfg, _   := config.NewConfig()
store, _ := storage.New(100)
h, _     := controller.New(store, cfg.BaseURL)
```

Благодаря этому хранилище в памяти можно заменить на PostgreSQL, не трогая обработчики.

### Конкурентность

Echo обрабатывает каждый запрос в отдельной горутине. Хранилище защищено `sync.RWMutex`:

- запись (создание канала, приём веб-хука) берёт эксклюзивную блокировку;
- чтение списка запросов берёт разделяемую блокировку, поэтому несколько чтений идут параллельно;
- наружу отдаётся копия данных, чтобы сериализация в JSON не пересекалась с записью.
