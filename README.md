# "Коллектор веб-хуков" (а-ля webhook.site)

Этот сервис предоставляет пользователям уникальный URL, на который они могут отправлять любые HTTP-запросы (веб-хуки) от других сервисов (например, GitHub, Stripe, Telegram). Наш сервис будет ловить эти запросы, сохранять их и отображать пользователю в удобном виде.

**Почему это хороший проект:**

*   **Работа с "сырыми" данными:** Учит парсить разнообразные входящие запросы (JSON, XML, form-data), работать с заголовками, методами — это отличная практика для бэкенд-разработчика.
*   **Очевидная польза RabbitMQ:** Главная задача эндпоинта, принимающего веб-хук, — ответить максимально быстро (`200 OK`), чтобы отправляющий сервис не посчитал доставку неуспешной. Всю "медленную" работу (парсинг, сохранение в БД) нужно делать асинхронно. Это идеальная, каноническая задача для брокера сообщений.
*   **Работа с JSON в Postgres:** Данные веб-хуков неструктурированы. Их идеально хранить в PostgreSQL, используя тип данных `JSONB`, что познакомит студентов с более продвинутыми возможностями базы данных.

**Основной функционал:**

1.  **API эндпоинт `POST /api/v1/hooks`**:
    *   Генерирует уникальный идентификатор для нового "канала" веб-хуков.
    *   Возвращает URL для приема веб-хуков, например: `http://localhost:8080/wh/{уникальный_id}`.
2.  **Эндпоинт `ANY /{уникальный_id}`**:
    *   Это "ловушка" для веб-хуков. Принимает любой метод (`POST`, `GET`, `PUT`).
    *   Собирает всю информацию о запросе: метод, заголовки, тело запроса, IP-адрес источника.
    *   Упаковывает все эти данные в сообщение и **мгновенно** отправляет в очередь RabbitMQ.
    *   Немедленно отвечает `200 OK`.
3.  **Воркер:**
    *   Слушает очередь RabbitMQ.
    *   Получив сообщение, разбирает его и сохраняет всю информацию о принятом веб-хуке в таблицу `requests` в PostgreSQL (с привязкой к `уникальному_id`).
4.  **API эндпоинт `GET /api/v1/hooks/{уникальный_id}/requests`**:
    *   Отдает список всех сохраненных запросов для данного канала в формате JSON, чтобы пользователь мог их просмотреть.
