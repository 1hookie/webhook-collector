# Инструкция для студентов: как сдать домашнее задание

Весь курс у каждого студента **свой личный репозиторий** на GitLab. Домашние задания сдаются через **merge request (MR)**: вы делаете работу в ветке, отправляете MR, преподаватель проверяет, и после одобрения вы сами сливаете изменения в `main`.

## Как проходит жизнь одного задания

```
обновить main
  → создать ветку hw-NN
  → работать, коммитить, пушить
  → открыть MR (с заполненным шаблоном и меткой)
  → проверка преподавателем
      ├─ есть замечания → исправить в ТОЙ ЖЕ ветке, ответить «done» → повторная проверка
      └─ одобрено (approved) → вы жмёте Merge → ветка удаляется → следующее ДЗ
```

Правило: **одно задание = одна ветка = один MR**. Следующее задание начинаете только после того, как предыдущее слито в `main`.

## Разовая подготовка

- У вас уже есть доступ к вашему репозиторию (ссылку выдаёт преподаватель).
- Если `git clone` / `git push` не работают — обратитесь к преподавателю (проблема с ключами/токеном решается за минуту), не ломайте голову самостоятельно.

## Шаг 1. Подготовьте main

Перед началом любого нового задания:

```bash
git checkout main
git pull origin main
```

Начинайте новое ДЗ только из чистого и актуального `main`.

## Шаг 2. Создайте ветку

Имя ветки совпадает с номером задания: `hw-01`, `hw-02`, … `hw-11`.

```bash
git checkout -b hw-04
```

## Шаг 3. Работайте и пушите

- Коммить можно сколько угодно раз, сообщения — короткие и по смыслу («добавил таблицу requests», «исправил теги json»).
- Пушьте часто — всё запушенное лежит на сервере и никуда не теряется:

```bash
git push -u origin hw-04    # первый раз именно так (с -u)
git push                    # все последующие разы
```

## Шаг 4. Проверьте код: golangci-lint

Прежде чем пушить и открывать MR, прогоните статический анализатор (линтер):

```bash
golangci-lint run
```

- Ставится один раз: `go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest`. Бинарник кладётся в `~/go/bin` — убедитесь, что эта папка есть в `PATH` (как делалось при установке Go).
- Настройки лежат в корне репозитория в файле `.golangci-lint.yaml`. Его менять без просьбы преподавателя не нужно.
- Если команда ничего не напечатала и завершилась с кодом 0 — всё чисто, можно пушить.
- Если перечислила файлы с проблемами — прочитайте каждое замечание: оно начинается с названием линтера в скобках (`(errcheck)`, `(unused)` …) и говорит, что не так. Исправьте код, прогоните снова — до тишины.
- Типичные находки: непроверенная ошибка (`err` «в никуда»), неиспользуемая переменная или функция, незакрытый HTTP-ответ, бессмысленное присваивание.
- Тот же самый шаг выполняет CI при открытии MR: красный пайплайн из-за линтера = MR вернут без чтения. Локальный прогон экономит один круг «пуш → краснота → правка → ещё пуш».

## Шаг 5. Откройте Merge Request

Сразу после первого пуша на странице репозитория появится кнопка **«Create merge request»** (или: меню *Merge requests* → *New merge request*).

Заполните:

| Поле  | Что написать   |
|------ |-------------- |
| Source branch | ваша ветка, например `hw-04` (уже подставлено) |
| Target branch | `main` (не меняйте) |
| Assignee  | указать себя |
| Reviewer  | указать преподавателя  |
| Title | `ДЗ 4: БД, миграции, синхронное сохранение` — номер и суть |
| Description | GitLab сам подставит шаблон — **заполните все секции**: что сделано, вывод проверок curl (вставьте реальный вывод!), ответ на вопрос задания, чек-лист самопроверки |
| Labels | обязательно поставьте метку `hw-04` (без неё задание теряется в учёте) |

Жмите **Create merge request**. Дальше MR идёт в очередь на проверку — это нормально, проверяют всех подряд. О новых событиях по вашему MR GitLab шлёт письмо на почту.

## Шаг 6. Работа с замечаниями

Замечания приходят прямо в MR: либо привязаны к конкретной строке кода, либо общим комментарием. Порядок работы с каждым замечанием:

1. **Прочитать внимательно.** Неясно — задайте уточняющий вопрос в этом же обсуждении (thread). Спрашивать — нормально и даже хорошо.
2. **Исправить код** и запушить изменение **в ту же ветку** `hw-04`.
   ⚠️ Не создавайте новую ветку и новый MR для исправлений — MR обновится автоматически при пуше в исходную ветку.
3. **Ответить в этом же обсуждении словом `done`** — после слова done я знаю, что можно перепроверять именно этот комментарий.
4. **Не закрывайте (Resolve) обсуждение самостоятельно** — закрывает проверяющий.

Если вы **не согласны** с замечанием — напишите в обсуждении своё обоснование (почему так лучше/правильно), а не просто «done». Разберём вместе.

Когда все обсуждения отработаны, я перепроверяю MR целиком: либо приходят новые замечания (повторяем шаги 1–4), либо ставлю одобрение.

## Шаг 7. Слияние после одобрения

Когда вы видите:

- отметку **Approved** (одобрено преподавателем),
- зелёный пайплайн CI (файчик-галочка у коммитов),
- все обсуждения закрыты,

— возвращайтесь в MR и жмите большую зелёную кнопку **Merge**.

- Убедитесь, что отмечен чекбокс **«Delete source branch»** (отмечен по умолчанию) — ветка удалится после слияния, это правильно.
- Без одобрения и без зелёного пайплина кнопка Merge не сработает — `main` защищён. Прямой `git push` в `main` тоже невозможен. Обходить защиту не пытайтесь.

После мержа задание сдано. Заберите следующее ДЗ по кругу из схемы в начале документа.

## Правила коротко

1. Одно задание — одна ветка — один MR.
2. Исправления к замечаниям — в ту же ветку, не в новый MR.
3. На каждое исправленное замечание — ответ `done` в его обсуждении.
4. Обсуждения не закрываем сами.
5. Историю не переписываем: никаких `rebase`, `reset --hard` и `push --force`. Сломали историю — сообщите преподавателю.
6. Перед созданием MR — `golangci-lint run` прошёл без замечаний.
7. Новое задание — только из актуального `main` и только после мержа предыдущего.

## Типичные ситуации

- **Заметил ошибку уже после мержа.** Спокойно: создаёте новую ветку `fix/hw-04` из `main`, чините, открываете маленький отдельный MR. Такое бывает, это нормальная практика.
- **Ветка сильно сломана, проще начать заново.** Худший случай — пересоздать ветку из `main` и переделать работу. Всё, что вы успели запушить, не потеряно и лежит на сервере; восстановить коммиты преподаватель может за пару минут. Сообщите о проблеме.
- **Конфликт при мерже или пуше.** Обычно причина — стартовали из неактуального `main`. Лечится: `git pull origin main` в своей ветке, разрешить конфликт, запушить. Если сложно — покажите текст ошибки преподавателю.
- **MR висит без движения долго.** Напишите мне — напомню, что ваш в очереди.

## Мини-словарь

| Термин | Что значит |
|--------|-----------|
| ветка (branch) | независимая линия изменений; у каждого ДЗ своя |
| `main` | «священная» ветка с актуальным состоянием проекта; в неё попадает только проверенный код |
| коммит (commit) | фиксация снимка изменений с подписью и комментарием |
| push / pull | отправить свои коммиты на сервер / забрать свежие со сервера |
| merge request (MR) | запрос «слийте мою ветку в main»; место, где выносится код на проверку |
| approval (одобрение) | отметка преподавателя «можно сливать» |
| merge | фактическое слияние ветки в `main`; кнопку жмёте вы после одобрения |
| конфликт (conflict) | две правки попали в одно место; приходится разрешать руками |
