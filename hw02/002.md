## Слайд 5

**Заголовок** -- функция copy

Встроенная функция copy в Go предназначена для копирования элементов из одного слайса в другой. Она принимает два аргумента: слайс-приемник (destination) и слайс-источник (source), после чего копирует количество элементов, равное минимальной длине из этих двух слайсов, и возвращает фактическое число скопированных элементов. Функция корректно обрабатывает случаи, когда области памяти слайсов перекрываются, однако важно помнить, что встроенный copy работает только со слайсами и не поддерживает словари (map). Для копирования словарей необходимо использовать цикл или функцию maps.Copy из стандартной библиотеки (добавленную в Go 1.21).

```go
package main

import (
	"fmt"
	"maps"
)

func main() {
	srcSlice := []int{1, 2, 3, 4, 5}
	dstSlice := make([]int, 3) 

	copiedCount := copy(dstSlice, srcSlice)
	
	fmt.Printf("Слайс: %v | Скопировано элементов: %d\n", dstSlice, copiedCount)
	fmt.Println("--------")
    
	srcMap := map[string]int{"apple": 1, "banana": 2, "orange": 3}
	dstMap := make(map[string]int, len(srcMap))
	maps.Copy(dstMap, srcMap)
}
```


## Слайд 6

**Заголовок** -- указатели

Указатели в Go — это специальные переменные, которые хранят адрес памяти другой переменной, позволяя обращаться к данным по ссылке, а не копировать их по значению. Для получения адреса переменной используется оператор `&`, а для объявления типа указателя и разыменования (получения значения по адресу) — оператор `*`. Указатели в Go применяются преимущественно для оптимизации производительности (чтобы избежать затратного копирования больших структур при передаче в функции) и для обеспечения изменяемости данных (когда функции или методы должны модифицировать оригинальный объект, а не его локальную копию). 

```go
package main

import (
	"fmt"
)

func main() {
	a := 1
	fmt.Println("1::",a)
	foo(a)
	fmt.Println("4::",a)
}

func foo(a int) {
	fmt.Println("\t2::",a)
	a = 2
	fmt.Println("\t3::",a)
}
```

```
1:: 1
	2:: 1
	3:: 2
4:: 1
```

```go
package main

import (
	"fmt"
)

func main() {
	a := 1
	fmt.Println("1::",a)
	foo(&a)
	fmt.Println("4::",a)
}

func foo(a *int) {
	fmt.Println("\t2::",*a)
	*a = 2
	fmt.Println("\t3::",*a)
}
```

```

	2:: 1
	3:: 2
4:: 2

package main

import (
	"fmt"
	"net/http"
	"time"
)

func main() {
	http.HandleFunc("/", func(responseWriter http.ResponseWriter, request *http.Request) {
		method := request.Method
		uri := request.RequestURI

		responseWriter.Header().Set("X-Current-Time", time.Now().String())
		responseWriter.Header().Set("Content-Type", "text/plain; charset=utf-8")

		responseWriter.WriteHeader(http.StatusOK)
		_, err := responseWriter.Write([]byte(fmt.Sprintf("method=%s, uri=%s\n", method, uri)))
		if err != nil {
			panic(err)
		}

	})
	if err := http.ListenAndServe(":8080", nil); err != nil {
		fmt.Println("Ошибка запуска сервера:", err)
	}
	fmt.Println("Сервер запущен на http://localhost:8080")
}

## Слайд 15

**Заголовок** -- зачем нужна система контроля версий

Работая с файлами напрямую, мы теряем историю: непонятно, какая версия кода «работала», нельзя откатить сломанное состояние, и невозможно передать промежуточный результат на проверку (например, домашнее задание преподавателю).

Система контроля версий (VCS) решает это: каждое изменение фиксируется снимком (коммитом), сохраняется полная история проекта, и в любой момент можно вернуться к прошлому состоянию. В курсе используем **git**, а проекты храним на сервере **GitLab**.

## Слайд 16

**Заголовок** -- Базовые термины VCS:

| Термин | Что это |
|--------|---------|
| репозиторий (repo) | папка проекта под контролем версий (содержит скрытую директорию `.git`) |
| коммит | зафиксированный снимок изменений с автором и сообщением |
| ветка (branch) | независимая линия разработки; `main` — основная |
| remote (удалённый репозиторий) | копия репозитория на сервере (в GitLab) |
| push / pull | отправить локальные коммиты на сервер / получить изменения с сервера |

```

```bash
# ветки

git merge hw-01           # влить ветку в текущую (в нашем режиме — через MR!)
```

Два правила курса:

- Сообщения коммитов — короткие и осмысленные: «добавил таблицу requests», а не «fix».
- В рабочем режиме задания прямо в `main` не пушим: работает схема «ветка → merge request → мерж» (следующий слайд).

  → git checkout -b hw-NN          # ветка под номером задания

Подробности (шаблон MR, метки, ответы «done» на замечания) — в инструкции для студентов. Главная идея: **одно задание — одна ветка — один MR**.

## Слайд 19

**Заголовок** -- статический анализ: golangci-lint

Компилятор ловит ошибки типов, но прощает то, что «компилируется, но явно написано неверно»: непроверенные ошибки, неиспользуемые переменные, незакрытые ресурсы. Статические анализаторы (линтеры) ловят именно такое. **golangci-lint** — агрегатор Go-linters: один бинарник, десятки проверок, единый вывод.

```bash
# установка (один раз)
go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest

# запуск в корне проекта
golangci-lint run
```

Пример находки:

```
controller/user_controller.go:41:12: Error return value of `ctrl.db.Query` is not checked (errcheck)
        rows, err := ctrl.db.Query("select id,name from test")
```

Если замечаний нет — команда молча завершается с кодом 0. С этого момента правило простое: **перед сдачей задания `golangci-lint run` должен пройти без замечаний**. В CI этот шаг выполняется автоматически, но прогонять его стоит локально — так правки быстрее.

## Слайд 20

**Заголовок** -- конфигурация golangci-lint: .golangci-lint.yaml

Конфигурационный файл лежит в корне репозитория вместе с остальным кодом. Его вы получаете готовым в шаблоне репозитория — задача: понимать, что внутри.

```yaml
# .golangci-lint.yaml
version: "2"

run:
  timeout: 5m
  modules-download-mode: vendor    # зависимости берём из vendor/, интернет не нужен

linters:
  default: standard                # базовый набор: errcheck, govet, staticcheck,
                                   # gosimple, ineffassign, unused
  enable:
    - bodyclose                    # дополнительно: тела HTTP-ответов закрыты?

issues:
  exclude-rules:
    - path: _test\.go              # тесты освобождаем от двух самых придирчивых
      linters:
        - errcheck
        - bodyclose
```

## Слайд 21

**Заголовок** -- конфигурация golangci-lint: .golangci-lint.yaml

| Секция | Что делает |
|--------|-----------|
| `run.modules-download-mode: vendor` | анализ идёт по зависимостям из `vendor/` — вспомним слайд про вендоринг |
| `linters.default: standard` | базовый набор проверок |
| `linters.enable: bodyclose` | отдельная проверка: закрыл ли ты тело HTTP-ответа после чтения |
| `issues.exclude-rules` | в `_test.go` не ругаемся на errcheck/bodyclose — в тестах ошибки иногда обрабатывают по-своему |

Требование к каждому заданию: зелёный pайплайн = чистое форматирование + чистый линтер. Красный пайплин не даст вам же мержнуть свой MR.
